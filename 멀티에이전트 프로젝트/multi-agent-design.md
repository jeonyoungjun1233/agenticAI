# 멀티에이전트 작업 설계도

## 1. 설계 목적

이 문서는 기존 `콩쌤 수박게임` 프로젝트의 게임 코드를 수정하지 않고, 과제 제출을 위해 멀티에이전트 작업 구조를 설계한 문서이다.  
목표는 여러 AI 에이전트가 같은 프로젝트를 다룰 때 어떤 역할을 나누고, 어떤 순서로 협업하며, 어떤 정보를 공유해야 안전하게 작업할 수 있는지 설명하는 것이다.

이 설계도는 별도 폴더로 옮겨도 이해될 수 있도록 독립 문서로 작성한다.

## 2. 단일 에이전트의 한계

단일 에이전트는 한 번에 하나의 관점으로 작업을 처리한다. 간단한 수정이나 짧은 문서 작성에는 효율적이지만, 작업 구조가 복잡해질수록 다음과 같은 한계가 생긴다.

### 2.1 작업 병목

하나의 에이전트가 요구사항 분석, 코드 구조 파악, 문서 작성, 테스트, 검토를 모두 담당하면 작업이 순차적으로만 진행된다.  
여러 영역을 동시에 확인할 수 없기 때문에 시간이 오래 걸리고, 특정 단계에서 막히면 전체 작업이 멈춘다.

### 2.2 역할 충돌

개발자 역할과 검토자 역할을 같은 에이전트가 동시에 맡으면 자신이 만든 결과를 스스로 객관적으로 검토하기 어렵다.  
예를 들어 문서를 작성한 에이전트가 바로 검토까지 하면 빠진 설명이나 애매한 표현을 놓칠 가능성이 높다.

### 2.3 문맥 과부하

프로젝트 요구사항, 코드 구조, 테스트 결과, 제출 조건을 모두 하나의 대화 문맥에 담으면 중요한 정보가 묻힐 수 있다.  
특히 파일이 많아지거나 수정 조건이 엄격할수록 에이전트가 이전 제약을 잊고 불필요한 변경을 할 위험이 커진다.

### 2.4 검증 사각지대

단일 에이전트는 작업 결과를 빠르게 만들 수 있지만, 결과가 요구사항을 모두 만족하는지 독립적으로 확인하는 과정이 약하다.  
예를 들어 "게임 코드는 건드리지 않는다"는 조건이 있을 때, 별도의 리뷰 에이전트가 변경 파일 목록을 확인하면 실수를 줄일 수 있다.

## 3. 멀티에이전트의 4대 패턴

멀티에이전트는 여러 에이전트가 역할을 나누어 하나의 목표를 달성하는 구조이다. 대표적인 패턴은 계층형, 협력형, 순차형, 시장형이다.

### 3.1 계층형 패턴

계층형 패턴은 관리자 에이전트가 전체 목표를 나누고, 하위 에이전트에게 작업을 배정하는 방식이다.

- 특징: 상위 에이전트가 계획, 우선순위, 최종 판단을 담당한다.
- 장점: 책임자가 명확하고 작업 범위를 통제하기 쉽다.
- 단점: 관리자 에이전트의 판단이 틀리면 전체 방향이 흔들릴 수 있다.
- 적합한 작업: 과제 제출, 문서 구조화, 기능 개발처럼 전체 흐름 관리가 필요한 작업.

이 프로젝트에서는 프로젝트 매니저 에이전트가 요구사항을 정리하고, 문서화 에이전트와 검토 에이전트에게 작업을 나누는 구조에 사용할 수 있다.

### 3.2 협력형 패턴

협력형 패턴은 여러 에이전트가 같은 문제를 서로 다른 관점에서 동시에 검토하고 의견을 합치는 방식이다.

- 특징: 각 에이전트가 독립적으로 분석한 뒤 결과를 비교한다.
- 장점: 빠진 부분을 찾기 좋고, 다양한 관점을 반영할 수 있다.
- 단점: 의견 충돌이 생기면 조율 과정이 필요하다.
- 적합한 작업: 설계 리뷰, 위험 분석, 아이디어 비교, 문서 개선.

이 프로젝트에서는 개발 관점 에이전트가 "코드에 영향이 있는가"를 보고, 문서 관점 에이전트가 "제출 문서가 이해하기 쉬운가"를 동시에 검토할 수 있다.

### 3.3 순차형 패턴

순차형 패턴은 한 에이전트의 결과물을 다음 에이전트가 이어받아 작업하는 방식이다.

- 특징: 작업이 단계별로 흐른다.
- 장점: 산출물의 흐름이 명확하고, 이전 단계 결과를 바탕으로 다음 작업을 하기 쉽다.
- 단점: 앞 단계가 늦어지면 뒤 단계도 모두 늦어진다.
- 적합한 작업: 요구사항 정리 → 초안 작성 → 검토 → 최종 정리처럼 순서가 중요한 작업.

이 프로젝트에서는 요구사항 정리 에이전트가 먼저 과제 조건을 정리하고, 문서 작성 에이전트가 설계도를 만들고, 리뷰 에이전트가 최종 확인하는 흐름이 적합하다.

### 3.4 시장형 패턴

시장형 패턴은 여러 에이전트가 작업 제안이나 해결책을 내고, 가장 적합한 결과를 선택하는 방식이다.

- 특징: 여러 후보 결과를 비교하여 선택한다.
- 장점: 다양한 해결안을 빠르게 얻을 수 있다.
- 단점: 선택 기준이 없으면 결과가 산만해질 수 있다.
- 적합한 작업: 설계안 후보 비교, UI 시안 비교, 프롬프트 전략 비교.

이 프로젝트에서는 "문서 중심 멀티에이전트 설계", "개발 중심 멀티에이전트 설계", "QA 중심 멀티에이전트 설계" 같은 후보를 만든 뒤, 과제 목적에 가장 맞는 문서 중심 설계를 선택할 수 있다.

## 4. 핸드오프와 공유 메모리의 역할

멀티에이전트 작업에서 중요한 것은 에이전트 수가 아니라, 에이전트 사이의 연결 방식이다.  
핸드오프와 공유 메모리는 그 연결을 안정적으로 만드는 장치이다.

### 4.1 핸드오프

핸드오프는 한 에이전트가 작업을 마치고 다음 에이전트에게 필요한 정보를 넘기는 과정이다.

핸드오프에는 다음 내용이 포함되어야 한다.

- 작업 목표
- 완료한 내용
- 아직 남은 내용
- 수정하거나 건드리면 안 되는 파일
- 판단이 필요한 질문
- 검토해야 할 위험 요소

예를 들어 문서 작성 에이전트가 리뷰 에이전트에게 넘길 때는 "게임 코드는 수정하지 않았고, 새 Markdown 문서만 작성했다"는 정보를 반드시 전달해야 한다.

### 4.2 공유 메모리

공유 메모리는 모든 에이전트가 함께 참고하는 공통 기록이다.

공유 메모리에는 다음 정보가 들어간다.

- 프로젝트 목적
- 현재 제약 조건
- 에이전트별 역할
- 작업 진행 상태
- 변경된 파일 목록
- 최종 제출 체크리스트

이 프로젝트에서는 `multi-agent-project` 폴더 안의 Markdown 문서들이 공유 메모리 역할을 한다.  
모든 에이전트는 이 폴더의 문서를 기준으로 작업하고, `src`, `public`, `index.html`, `package.json` 같은 게임 실행 파일은 수정하지 않는다는 규칙을 공유해야 한다.

## 5. 멀티에이전트가 필요한 작업과 쓰지 말아야 할 작업

### 5.1 멀티에이전트가 필요한 작업

멀티에이전트는 다음과 같은 작업에 적합하다.

- 요구사항이 여러 개이고 서로 충돌할 수 있는 작업
- 기획, 개발, 테스트, 문서화가 함께 필요한 작업
- 결과물 검토가 중요한 작업
- 작업 범위를 엄격히 지켜야 하는 작업
- 여러 관점의 판단이 필요한 작업

내 프로젝트에서는 "게임 코드는 수정하지 않고 멀티에이전트 작업 설계 문서만 만든다"는 조건이 중요하다.  
따라서 프로젝트 매니저, 문서 작성, 코드 영향 검토, 최종 리뷰 역할을 나누면 실수 가능성을 줄일 수 있다.

### 5.2 멀티에이전트를 쓰지 말아야 할 작업

멀티에이전트가 항상 좋은 것은 아니다. 다음과 같은 작업에는 오히려 과하다.

- 오타 하나 수정하기
- 짧은 문장 하나 바꾸기
- 파일 하나만 확인하면 되는 단순 작업
- 즉시 처리해야 하는 작은 명령 실행
- 에이전트 간 조율 비용이 작업 자체보다 큰 경우

예를 들어 버튼 문구 하나를 바꾸는 정도라면 단일 에이전트가 빠르다.  
반대로 과제 제출 구조를 잡고, 역할을 설명하고, 수정 금지 조건을 지키며, 최종 검토까지 해야 한다면 멀티에이전트 구조가 더 적합하다.

## 6. 내 도메인의 멀티에이전트 설계안

### 6.1 도메인 정의

내 도메인은 `콩쌤 수박게임` 프로젝트를 기반으로 한 과제 제출용 개발 문서화 작업이다.  
핵심 목표는 게임 기능을 바꾸는 것이 아니라, 기존 게임 프로젝트 위에 멀티에이전트 작업 구조를 설명하는 문서 체계를 만드는 것이다.

### 6.2 적용할 패턴

이 프로젝트에는 하나의 패턴만 쓰기보다 다음과 같은 혼합 구조가 적합하다.

- 기본 구조: 계층형
- 작업 흐름: 순차형
- 검토 방식: 협력형
- 대안 비교가 필요할 때만 시장형

즉, 프로젝트 매니저 에이전트가 전체 방향을 잡고, 요구사항 정리 → 문서 작성 → 코드 영향 검토 → 최종 리뷰 순서로 진행한다.  
필요하면 여러 문서 구조 후보를 비교하는 시장형 방식을 일부 사용한다.

## 7. 에이전트 역할 설계

### 7.1 프로젝트 매니저 에이전트

역할:

- 과제 요구사항을 정리한다.
- 작업 범위와 수정 금지 대상을 정한다.
- 각 에이전트에게 역할을 배정한다.
- 최종 제출 기준을 확인한다.

산출물:

- 작업 목표
- 작업 순서
- 제출 체크리스트

### 7.2 컨텍스트 분석 에이전트

역할:

- 프로젝트 폴더 구조를 확인한다.
- 게임 코드와 문서 폴더를 구분한다.
- 수정하면 안 되는 파일을 명확히 한다.

산출물:

- 프로젝트 구조 요약
- 수정 가능 파일과 수정 금지 파일 목록

### 7.3 문서 작성 에이전트

역할:

- 멀티에이전트 개념을 과제 요구사항에 맞게 설명한다.
- 단일 에이전트 한계와 4대 패턴을 정리한다.
- 내 프로젝트에 맞는 설계도를 작성한다.

산출물:

- 멀티에이전트 설계 문서
- 발표나 제출에 사용할 수 있는 설명 문장

### 7.4 QA 에이전트

역할:

- 게임 코드가 수정되지 않았는지 확인한다.
- 문서가 요구사항을 빠짐없이 포함하는지 확인한다.
- 이동 가능한 독립 문서인지 확인한다.

산출물:

- 검토 결과
- 누락된 요구사항 목록
- 수정 제안

### 7.5 최종 리뷰 에이전트

역할:

- 전체 문서의 흐름을 검토한다.
- 표현이 자연스러운지 확인한다.
- 제출 조건과 실제 결과가 일치하는지 최종 판단한다.

산출물:

- 최종 승인 여부
- 제출 전 체크리스트

## 8. 작업 흐름

1. 프로젝트 매니저 에이전트가 과제 요구사항을 정리한다.
2. 컨텍스트 분석 에이전트가 프로젝트 구조와 수정 금지 파일을 확인한다.
3. 문서 작성 에이전트가 설계 문서 초안을 만든다.
4. QA 에이전트가 게임 코드 변경 여부와 요구사항 충족 여부를 확인한다.
5. 최종 리뷰 에이전트가 문서의 완성도와 제출 가능성을 판단한다.
6. 프로젝트 매니저 에이전트가 최종 제출 메시지를 정리한다.

## 9. 핸드오프 예시

다음은 이 프로젝트에서 사용할 수 있는 핸드오프 양식이다.

```text
[핸드오프]
보낸 에이전트:
받는 에이전트:
현재 목표:
완료한 작업:
남은 작업:
수정한 파일:
수정 금지 파일:
주의할 점:
검토 요청:
```

예시:

```text
[핸드오프]
보낸 에이전트: 문서 작성 에이전트
받는 에이전트: QA 에이전트
현재 목표: 과제 제출용 멀티에이전트 설계 문서 검토
완료한 작업: 단일 에이전트 한계, 4대 패턴, 핸드오프, 공유 메모리, 프로젝트 설계안 작성
남은 작업: 요구사항 누락 여부 확인
수정한 파일: multi-agent-project/multi-agent-design.md
수정 금지 파일: src, public, index.html, package.json, package-lock.json
주의할 점: 게임 기능은 변경하지 않아야 함
검토 요청: 문서가 별도 폴더로 이동되어도 이해 가능한지 확인
```

## 10. 공유 메모리 구조

이 프로젝트에서 공유 메모리는 다음과 같이 구성할 수 있다.

```text
multi-agent-project/
  AGENTS.md                전체 에이전트 공통 규칙
  GEMINI.md                보조 에이전트 작업 지침
  context.md               프로젝트 배경과 제약 조건
  todo.md                  작업 진행 상태
  multi-agent-design.md    제출용 멀티에이전트 설계도
```

공유 메모리에 반드시 남겨야 할 핵심 규칙은 다음과 같다.

- 게임 실행 코드는 수정하지 않는다.
- 문서 작업은 `multi-agent-project` 폴더 안에서만 진행한다.
- 각 에이전트는 자신의 역할과 산출물을 명확히 남긴다.
- 최종 검토 단계에서 변경 파일 목록을 확인한다.

## 11. 최종 판단

이 프로젝트는 단순히 코드 한 줄을 바꾸는 작업이 아니라, 과제 요구사항을 해석하고, 여러 역할을 나누고, 수정 금지 조건을 지키며, 제출 가능한 문서 구조를 만드는 작업이다.  
따라서 단일 에이전트보다 멀티에이전트 설계가 더 적합하다.

다만 실제 게임 기능을 추가하거나 작은 문장만 고치는 작업이라면 멀티에이전트를 쓰지 않아도 된다.  
이번 작업에서는 계층형을 중심으로 순차형과 협력형을 섞은 문서 중심 멀티에이전트 구조가 가장 적절하다.

## 12. 제출용 요약

이 설계안은 기존 수박게임 프로젝트를 수정하지 않고, 멀티에이전트 작업 구조를 문서로 설명하기 위한 것이다.  
단일 에이전트는 모든 역할을 혼자 처리하기 때문에 작업 병목, 역할 충돌, 문맥 과부하, 검증 사각지대가 생길 수 있다.  
이를 해결하기 위해 프로젝트 매니저, 컨텍스트 분석, 문서 작성, QA, 최종 리뷰 에이전트로 역할을 나누고, 핸드오프와 공유 메모리를 통해 작업 정보를 이어받도록 설계했다.  
본 프로젝트에는 계층형 구조를 기본으로 하고, 실제 작업 흐름은 순차형으로 진행하며, 검토 단계에서는 협력형을 사용하는 방식이 적합하다.
